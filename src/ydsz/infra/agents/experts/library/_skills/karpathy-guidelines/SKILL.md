# Karpathy 编码准则

基于 Andrej Karpathy 公开演讲和工作流提炼的 AI 编码框架，适用于所有 LLM 辅助编程场景。

## 核心原则

把 LLM 当作"能力极强但经验为零的实习生"：

1. **给上下文** — LLM 不会读心术，它需要知道你用的是什么框架、约定、测试环境
2. **给验证** — 不可信的产出，只有验证通过的产出才能合入
3. **给边界** — 限定范围，不要期望 AI 理解整个项目的隐式知识
4. **给反馈** — 每次交互都要纠正越界行为，防止累积偏差

> AI 擅长模式匹配，但不具备工程判断力。架构决策、权衡取舍、最终质量把控始终是人负责的。

## 提示设计 5 法则（RTOCF）

| 要素 | 说明 | 示例 |
| --- | --- | --- |
| **R**ole（角色） | 指定 AI 扮演的角色 | "你是一个精通 Django 的高级后端工程师" |
| **T**ask（任务） | 精确描述要做什么 | "为订单模块编写 CRUD API" |
| **C**onstraints（约束） | 技术栈、风格、禁止项 | "使用 DRF，遵循 PEP8，不使用 raw SQL" |
| **O**utput Format（输出格式） | 期望的返回结构 | "只输出代码 diff，附 3 行内注释" |
| **E**xamples（示例） | 1-2 个输入/输出样例 | "参考已有的 `/api/users/` 接口风格" |

### System Prompt 固定模板

在 system prompt 中一次性声明以下内容，避免每次重复：

```text
技术栈：Python 3.12 + FastAPI + SQLAlchemy 2.0
代码风格：Google Python Style Guide，max line length 100
测试框架：pytest，要求每个新功能附带 unit test
禁止项：不使用裸 except、不使用全局可变状态、不省略类型标注
输出格式：只输出变更部分，用 ```diff 包裹
```

## 上下文组织

**原则：提供受限上下文，而非全量 dump。**

| 反模式 | 推荐做法 |
| --- | --- |
| 把整个文件丢给 AI | 只给相关函数 + 接口签名 + 调用示例 |
| 粘贴全部错误日志 | 截取关键 10-20 行 + 错误码/异常类型 |
| 不给背景直接要求改动 | 先说清模块职责、数据流、改动目标 |
| 要求 AI "理解" 一个 5000 行项目 | 提供 architecture.md 或 README 摘要 |

### 上下文层级

1. **L1 项目级** — 架构文档、目录结构、编码规范（每次对话携带）
2. **L2 模块级** — 当前修改模块的接口定义、依赖关系
3. **L3 任务级** — 具体要改的函数 / 类 / 逻辑段

> 优先使用 L1+L3 组合，L2 仅在跨模块改动时加入。超出 AI 上下文窗口时用摘要替代全文。

## 增量验证环

```
AI 生成产出 → 编译/类型检查 → 运行测试 → 人工 Review → 合入
     ↑                                                      |
     └──────────── 未通过则回到 AI 修改 ←────────────────────┘
```

### 关键规则

1. **先写后验** — 让 AI 自带测试代码（test-first 思维），生成代码和测试一起产出
2. **有验证才推进** — 每次 AI 产出后立即跑 lint + test，未通过不进入下一步
3. **不信任直到验证通过** — AI 代码在测试通过前视为"未审核草稿"

### 反幻觉策略

| 策略 | 做法 |
| --- | --- |
| 要求引用来源 | "列出你参考的代码行号或文档路径" |
| 要求自验证 | "写出这段代码的 3 个边界条件并逐一测试" |
| 拆分任务 | 把大任务拆成 ≤50 行的子任务，逐一验证 |
| 锁住依赖 | 告诉 AI 具体版本号，避免生成不存在的 API |

## 反面模式

| 反模式 | 后果 | 对策 |
| --- | --- | --- |
| 一次改太多 | 难以定位错误，Review 成本爆炸 | 每次只改一个函数/类 |
| 相信未验证输出 | 引入隐蔽 bug | 跑过测试前不 merge |
| 无测试覆盖 | 回归无法发现 | 新代码必须陪同测试 |
| 提示过长无焦点 | AI 丢失关键信息 | 控制在 500 token 内，分段发送 |
| 接受第一个答案 | 错过更优方案 | 要求提供 2-3 个方案并对比 |

## 实战模板

### 代码生成提示模板

```text
[角色] 我是精通 {tech_stack} 的工程师，负责 {module} 模块。
[任务] 请帮我实现 {function_name}，功能描述：{description}
[约束]
- 输入类型：{input_types}
- 输出类型：{output_types}
- 错误处理：{error_handling_policy}
- 代码风格：{coding_style}
[参考] 现有类似实现：{reference_snippet_or_path}
[输出] 请输出：
1. 实现代码
2. 对应的 pytest 单元测试
3. 这段代码的潜在风险点
```

### Code Review 提示模板

```text
请用以下维度 Review 这段 diff：
1. 安全性：注入、越权、数据泄露
2. 性能：N+1 查询、内存泄漏、大循环
3. 正确性：边界条件、并发竞争、错误传播
4. 可维护性：命名清晰、单一职责、重复代码

风险分级：🔴 必须修复 / 🟡 建议改进 / 🟢 可选优化
每个发现给出：文件路径、行号、问题描述、修复建议。
```

### Bug 定位提示模板

```text
[现象] {symptom_description}
[上下文]
- 预期行为：{expected}
- 实际行为：{actual}
- 复现步骤：{reproduce_steps}
- 相关代码路径：{code_path}
- 错误日志：{error_tail}

请分析：
1. 根因（按可能性排序前 3 个）
2. 每个根因对应的排查命令
3. 修复方案和验证方法
```

## 使用指南

何时引用这份 skill：

- 准备用 AI 辅助编写、重构或调试代码时
- 设计 prompt 模板希望获得更稳定的 AI 产出时
- 团队制定 AI 编码规范或 best practice 时
- 需要向新人解释"为什么 AI 写的代码不能直接用"时

如何引用：在对应任务的 system prompt 或初始说明中注明"遵循 Karpathy 编码准则的 RTOCF 框架和增量验证环"。
