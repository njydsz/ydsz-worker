# Prompt Engineering 指南

提示工程（Prompt Engineering）是与大语言模型高效协作的核心技能。本指南从基础技巧到进阶框架，系统化呈现提示设计的方法论与最佳实践。

## 基础 6 技巧

### 1. 角色设定（Role Playing）
为模型赋予明确身份，约束其知识范围与表达风格。

```
你是一位资深 Python 后端工程师，擅长 FastAPI 与异步编程。请以专业视角回答以下问题。
```

**要点**：角色越具体，输出越聚焦；避免角色与任务冲突。

### 2. 任务分解（Task Decomposition）
将复杂任务拆为有序步骤，逐步引导模型完成。

```
请按以下步骤完成任务：
1. 分析输入数据的结构与类型
2. 识别潜在异常与边界条件
3. 给出处理方案并解释原因
4. 输出可执行代码
```

### 3. 输出格式约束（Output Formatting）
明确指定输出结构，便于后续解析与使用。

```
请以 JSON 格式输出，包含以下字段：
- summary: 一句话总结
- risks: 风险列表（数组）
- recommendation: 建议操作
```

### 4. 示例引导（Examples）
在提示中嵌入期望输出的示例，让模型"照猫画虎"。

```
将以下句子转为礼貌语气：
输入："这个功能做错了。"
输出："这个功能的实现方式似乎与预期有些出入，建议再确认一下需求。"

输入："代码又报错了。"
输出：
```

### 5. 否定约束（Negative Constraints）
明确告知模型"不要做什么"，减少无关或有害输出。

```
生成一段产品介绍，要求：
- 不要使用夸张修辞（如"最好"、"第一"）
- 不要包含未经证实的性能数据
- 不要超过 200 字
```

### 6. 少样本（Few-shot）
提供 2-5 个完整示例，让模型从中抽象规律。

```
根据示例格式，完成后续转换：
Q: 如何读取文件？→ A: with open('file.txt', 'r') as f: content = f.read()
Q: 如何写入 JSON？→ A: import json; with open('file.json', 'w') as f: json.dump(data, f)
Q: 如何遍历字典？→ A:
```

## 思维链 Chain-of-Thought (CoT)

CoT 引导模型在给出最终答案前展示推理过程，显著提升复杂任务的准确率。

### Zero-shot CoT
仅添加"请逐步思考"即可触发推理链。

```
一个水池有进水管和排水管。进水管单独注满需 3 小时，排水管单独排空需 6 小时。若同时打开两管，几小时能注满？请逐步思考。
```

### Few-shot CoT
提供带推理过程的示例作为模板。

```
Q: 小明有 5 个苹果，给小红 2 个，又买了 3 个，现在有几个？
A: 小明开始有 5 个。给出 2 个后剩余 5-2=3 个。再买 3 个后有 3+3=6 个。答案是 6。

Q: 书店有 120 本书，卖出 40 本，又进货 25 本，再卖出 30 本，现在有几本？
A:
```

### Step-by-step
显式要求模型列出每一步推理，适用于数学/逻辑题。

```
请按以下格式回答：
- 步骤 1: ...
- 步骤 2: ...
- 最终答案: ...
```

## ReAct 框架（Reasoning + Acting）

ReAct 让模型在**推理（Thought）**与**行动（Action）**之间交替循环，适用于需要工具调用或外部信息检索的场景。

```
Thought: 我需要查找当前北京的天气信息。
Action: call_weather_api(city="Beijing")
Observation: 北京当前气温 22°C，晴，湿度 45%

Thought: 已获得天气信息，可以为用户生成建议。
Action: generate_response(weather_data)
Observation: 建议穿着轻薄外套，适合户外活动

Thought: 信息完整，可以给出最终回答。
Answer: 北京今天天气晴好，气温 22°C，建议穿轻薄外套...
```

**核心循环**：Thought → Action → Observation → Thought → ... → Answer

## Reflexion 反思框架

Reflexion 在模型输出后进行自我评估与反思，将改进记忆应用于下次生成，实现"越用越好"。

```
[首次生成]
输出: <初始回答>

[自我评估]
评分: 7/10
不足: 缺少具体的性能优化建议，案例不够贴切

[改进记忆]
记住：在回答性能问题时，应包含：
1. 具体的指标数据
2. 优化前后的对比案例
3. 可操作的工具推荐

[二次生成（应用记忆后）]
输出: <改进后的回答>
```

**适用场景**：代码审查、文档撰写、方案评审等需要持续改进的任务。

## Prompt 调试清单（12 项）

在提交 Prompt 前，逐项检查：

| # | 检查项 | 说明 |
|---|--------|------|
| 1 | **清晰度** | 指令是否无歧义？模型能否用一句话复述任务？ |
| 2 | **完整性** | 是否提供了所有必要信息（上下文/数据/约束）？ |
| 3 | **一致性** | 多条指令间是否存在矛盾？ |
| 4 | **角色** | 角色设定是否与任务匹配？ |
| 5 | **边界** | 是否明确了"不做什么"的边界？ |
| 6 | **格式** | 输出格式是否具体且可解析？ |
| 7 | **样例** | 示例是否覆盖了典型和边界场景？ |
| 8 | **验证** | 模型是否知道如何自我验证答案？ |
| 9 | **可重复性** | 相同输入是否能得到稳定输出？ |
| 10 | **简洁性** | 是否去除了冗余信息？ |
| 11 | **兼容性** | 提示是否适配目标模型的能力边界？ |
| 12 | **安全性** | 是否存在被注入/越狱的风险？ |

## 效果评估 4 维度打分

每项 1-5 分，总分 20：

| 维度 | 5 分标准 | 1 分标准 |
|------|----------|----------|
| **一致性** | 多次输出高度一致，逻辑自洽 | 前后矛盾，结果随机 |
| **准确性** | 事实正确，推理无误 | 存在明显错误或幻觉 |
| **完整性** | 覆盖所有要求，无遗漏 | 关键信息缺失 |
| **简洁性** | 精炼无废话，直击要点 | 冗长啰嗦，重点模糊 |

## 行业案例速查

### 代码生成
```
你是有 10 年经验的 {language} 开发者。请根据以下需求编写代码：
- 功能描述: {description}
- 约束: 使用 {framework}，包含错误处理，时间复杂度不高于 O(n log n)
- 输出: 完整可运行代码 + 逐行注释 + 测试用例
```

### 文档撰写
```
请以专业技术文档风格撰写 {topic} 的说明文档：
- 目标读者: {audience}
- 结构: 概述 → 快速开始 → 详细说明 → 常见问题
- 字数: 1500-2000 字
- 语气: 专业但友好，避免居高临下
```

### 数据分析
```
你是一名数据科学家。请对以下数据集进行分析：
1. 数据概览（字段、类型、样本量）
2. 缺失值与异常值检测
3. 关键指标统计与可视化建议
4. 发现的规律与业务洞察
数据集描述: {dataset_desc}
```

### 翻译
```
请将以下 {source_lang} 文本翻译为 {target_lang}：
- 术语表: {glossary}
- 风格: {style}（正式/口语/技术文档）
- 要求: 保留原文格式，专业术语准确，符合目标语言习惯
原文: {text}
```

### 创意
```
请以 {writer_style} 的风格创作一篇关于 {theme} 的 {format}：
- 核心情绪: {mood}
- 目标受众: {audience}
- 字数: {word_count}
- 必须包含元素: {must_include}
- 避免元素: {must_avoid}
```

## 使用指南

1. **从简单开始**：先写最简 Prompt，按需叠加技巧
2. **迭代优化**：基于 12 项清单逐项改进
3. **版本管理**：记录每次修改与效果对比
4. **模板复用**：将验证有效的提示沉淀为模板
5. **评估驱动**：用 4 维度打分客观衡量改进效果
