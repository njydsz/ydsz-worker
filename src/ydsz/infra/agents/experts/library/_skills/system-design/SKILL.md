# 系统设计入门

系统设计的本质是在约束条件下做取舍。本方法论帮助架构师或面试者在 45-60 分钟内从模糊需求推导出一个合理、可演进的高层设计，并为深层优化设定方向。

## 一、四步流程

### 第 1 步：需求澄清（3-5 分钟）

不要急于画框图。先用结构化提问把"大概其"变成可设计的规格：

- **功能需求**：用户会做什么？（上传、搜索、发消息、支付……）哪些是 MVP 之外的？
- **非功能需求**：预期延迟 P99？可用性目标（几个 9）？一致性要求（强/最终/因果）？
- **规模量级**：DAU / MAU？读写比例？数据增长率（GB/天）？
- **约束条件**：团队规模？技术栈锁定？合规 / 数据驻留要求？

**判断标准**：每一步的需求都应该可以被量化和验证。"高性能" → "读 P99 < 200ms、写 P99 < 500ms"。

### 第 2 步：容量估算（5-10 分钟）

将需求转化为工程数字，决定资源形态：

| 估算项 | 公式 | 示例 |
| --- | --- | --- |
| QPS (读) | DAU × 每日操作数 × 读写比 / 86400 × 峰值系数 | 1000 万 DAU × 10 次 × 80% 读 / 86400 × 3 ≈ 28k QPS |
| QPS (写) | 同上 | ≈ 7k QPS |
| 存储量 | 日增量 × 保留天数 × 副本数 × 冗余系数 | 100GB/天 × 365 × 3 × 1.5 ≈ 160TB |
| 带宽 | QPS × 平均响应大小 × 8 | 28k × 5KB × 8 ≈ 1.1 Gbps |
| 后端实例数 | ⌈读 QPS / (单实例读吞吐 × 利用率)⌉ + ⌈写 QPS / (单实例写吞吐 × 利用率)⌉ | ⌈28k / (2000 × 0.7)⌉ = 20 读实例 |

常用量级记忆：单日 ≈ 10⁵ 秒、年 ≈ 3×10⁷ 秒、内存访问 ≈ 0.1ms、磁盘寻道 ≈ 10ms、同机房 RTT < 1ms、跨机房 RTT 30-100ms。

### 第 3 步：高层设计（20-30 分钟）

从 API → 数据模型 → 组件拓扑逐步展开：

1. **定义 API**：资源、动作、参数、响应格式。RESTful 或 Graph 按场景选择，明确分页与错误码约定。
2. **数据模型**：实体关系、主键选择（UUID / 雪花 ID / ULID）、存储选型（SQL for 关系强一致、NoSQL for 灵活 schema、对象存储 for 大 BLOB）。
3. **组件图**：客户端 → CDN → LB → 网关 → 微服务 → DB / 缓存 / MQ。标出同步调用（实线）与异步路径（虚线）。
4. **核心路径走读**：选取 2-3 个关键用例，沿组件图串行走读，标注每一跳的延迟预算和超时设置。

### 第 4 步：深层优化（10-15 分钟）

在高层框架落地后，识别瓶颈并讨论权衡：

- **性能瓶颈**：热点路径、N+1 查询、锁竞争、序列化开销。
- **可用性风险**：单点故障、级联故障、脑裂。
- **扩展性天花板**：单库容量上限、单队列吞吐量、冷启动长尾。

## 二、关键概念清单

每次设计至少评估以下维度并做取舍：

| 概念 | 核心取舍 | 适用场景 |
| --- | --- | --- |
| CAP / BASE | CP vs AP；强一致 vs 高可用 | 金融交易选 CP，社交 Feed 选 AP |
| 一致性模型 | 线性一致 → 顺序 → 因果 → 最终 | 用户余额线性一致，点赞计数最终一致 |
| 分片策略 | Range / Hash / Geo | Range 适合范围查询，Hash 分布均匀 |
| 复制拓扑 | 主从异步 / 同步多主 / Paxos/Raft | 日志记录用异步复制，选主用 Raft |
| 缓存策略 | Cache-Aside / Read-Through / Write-Behind | 通用模式 Cache-Aside，热点极高用 Write-Behind |
| 负载均衡 | L4 四层 / L7 四层半 + 健康检查 | 内部 RPC 用 L4，HTTP 用 L7 |
| 消息队列 | Partition 并行、Exactly-Once vs At-Least-Once | 事件溯源，削峰填谷 |

## 三、经典案例速查

| 案例 | 核心挑战 | 关键取舍 |
| --- | --- | --- |
| **URL Shortener** | 哈希冲突 / 重定向延迟 / 统计 | 用发号器 + Base62 避免冲突；CDN + 301 缓存；统计异步批写 |
| **即时聊天** | 消息有序 / 长连接管理 / 多端同步 | WebSocket + 心跳保活；消息序号单调递增；离线用推模型（APNs/FCM） |
| **News Feed** | 扇出爆炸 / 写入 pull vs 读取 push | 名人用户拉模型（fan-out on read），普通用户推模型（fan-out on write），混合策略 |
| **分布式缓存** | 雪崩 / 击穿 / 穿透 | 多 TTL 抖动防雪崩；互斥锁防击穿；布隆过滤器防穿透 |
| **Rate Limiter** | 滑动窗口精度 / 多节点一致性 | Token Bucket 单机或 Redis+Lua 集群；滑动日志用 Sorted Set |

## 四、设计文档模板

建议新系统在立项时复用以下结构（精简版本）：

```markdown
# [系统] 设计文档

## 背景
一句话说明为什么需要这个系统。

## 目标
- 功能性目标（量化：QPS、延迟、数据量）
- 非功能性目标（可用性 / 一致性 / 安全）

## 非目标（Out of Scope）
明确不包含的能力，避免范围蔓延。

## 高层架构
组件图 + 数据流（文字描述或 ASCII 框图）。

## 数据模型
核心表 / 集合 schema，主键策略。

## API 设计
关键接口的 method / path / request / response / 错误码。

## 容量规划
基于第 2 步估算得出的实例数、存储、带宽需求。

## 监控与告警
SLO / SLI 定义；关键指标：成功率、P99 延迟、错误率、资源水位。

## 风险与权衡
当前未解决的问题、已知限制、trade-off 记录。
```

## 五、常见反模式

1. **分布式单体**：服务拆分后仍然强耦合 → 独立部署失去意义，回退到 SOA 边界清晰化。
2. **无状态丢失**：把会话数据放本地内存 → 节点重启即丢；外移到 Redis / Sticky Session。
3. **缓存雪崩**：大量 key 同时 TTL → 抖动 TTL 或使用双层缓存（本地 + 分布式）。
4. **忽视网络分区**：假设网络永远可靠 → 设计时明确 CAP 取舍，引入超时与重试策略。
5. **过度抽象早期**：未验证需求就引入 CQRS / Event Sourcing → 先跑通再拆分，保持演进式架构。

## 使用指南

当用户提出"帮我设计一个 XX 系统"、"系统架构该怎么搞"或面试准备的类似请求时，按本 Skill 的四步流程推进。每个阶段向用户确认关键假设，必要时引用经典案例速查表做类比推理。最终交付物应包含高层架构描述、数据模型、容量估算和风险权衡。
