# Code Review 清单

## 问题分级（P0-P3）

### P0 — 阻塞发布

必须修复后方可合并，否则存在线上事故、数据丢失或安全漏洞风险：

- SQL 注入 / 命令注入 / XSS 等安全漏洞
- 认证或鉴权逻辑被绕过
- 数据丢失或不可逆的数据变更（无回滚方案）
- 敏感信息硬编码（密钥、密码、Token）
- 死循环或资源泄漏（连接未关闭、文件句柄未释放）
- 并发竞争条件导致数据不一致
- 核心流程断崖式错误（支付、订单状态机跳变）

**发布阻塞规则**：只要存在 1 个及以上 P0 项，PR 必须打 `blocked` 标签，CI 流水线标记为失败，禁止 merge。

### P1 — 严重问题

不阻塞当次发布但必须在当前 sprint 内修复，或作为 follow-up issue 创建并关联本 PR：

- 缺少关键错误处理（吞掉异常导致静默失败）
- 性能隐患：N+1 查询、未分页的大数据集遍历、锁粒度不当
- 边界条件未覆盖（空集合、超大输入、并发冲突）
- 缺少单元测试或集成测试覆盖核心路径
- 接口契约变更未同步文档

### P2 — 建议修复

建议在本次 PR 一并处理，可协商延后：

- 命名不清晰（缩写歧义、动词名词混用）
- 魔法数字 / 硬编码常量
- 函数超过 50 行或嵌套超过 3 层
- 缺少关键注释（Why 而非 What）
- 重复代码可抽取复用

### P3 — Nit（可选优化）

不要求修改，但可作为礼貌性建议：

- 格式 / 空行不一致
- 变量可早声明或晚声明
- import 顺序调整
- 注释措辞微调

## 六大维度 Checklist

### 一、安全（Security）

1. 所有外部输入是否经过校验和清洗？
2. 敏感数据是否脱敏或加密存储？日志中是否意外打印？
3. SQL 查询是否使用参数化绑定，避免拼接？
4. 鉴权/授权逻辑是否在服务端强制执行（不依赖前端隐藏）？
5. Token / 密钥是否走环境变量或密钥管理服务，而非硬编码？
6. 文件上传是否有类型、大小、内容校验？
7. 依赖库是否存在已知 CVE（自动扫描是否通过）？
8. HTTP 响应头是否包含安全相关头（CSP、HSTS、X-Content-Type-Options）？

### 二、性能（Performance）

1. 数据库查询是否有索引支撑？大表是否做了分页？
2. 是否存在 N+1 查询问题？能否改为批量加载？
3. 循环内部是否有网络请求 / IO 操作？
4. 是否有合适的数据结构选择（Set vs List 的 O(1) vs O(n)）？
5. 缓存策略是否合理？缓存 Key 是否可能冲突？
6. 大对象是否及时释放，避免内存泄漏？
7. 是否引入了不必要的同步阻塞？能否改为异步？
8. API 响应时间预估是否可接受？是否需要加超时控制？

### 三、可读性（Readability）

1. 命名是否自解释？能否在不看注释的情况下理解用途？
2. 函数/方法是否遵循单一职责？长度是否合理？
3. 条件分支是否有明确意图？是否需要卫语句提前返回？
4. 关键逻辑是否有 Why 型注释（而非 What 型重复代码）？
5. 缩进、空行、分组是否有助于视觉分区？
6. import 是否去除了未使用的模块？

### 四、测试（Testing）

1. 新增/修改的逻辑是否有对应的测试用例覆盖？
2. 边界条件（空值、极值、并发）是否有测试？
3. Mock/Stub 是否合理？是否过度 mock 失去测试意义？
4. 测试是否独立可重复？外部依赖是否解耦？
5. 错误路径是否覆盖（异常、超时、降级）？
6. 测试命名是否清晰描述场景和预期？（`test_<场景>_<预期行为>`）

### 五、架构（Architecture）

1. 是否遵循现有模块边界？是否越层调用？
2. 新增依赖是否合理？是否引入不必要的重型框架？
3. 接口设计是否向后兼容？是否遵循最小暴露原则？
4. 状态管理是否集中？是否存在散落多处的"隐式"状态？
5. 是否遵循 SOLID / DRY / KISS 等基本原则？
6. 新技术/模式是否在团队认知范围内，或有足够文档支撑？

### 六、规范（Conventions）

1. 代码风格是否符合 Linter / Formatter 规则？
2. Commit message 是否遵循 Conventional Commits 或团队约定？
3. PR 描述是否包含变更动机、影响范围、测试方案？
4. 是否更新了相关文档（README、API Docs、Changelog）？
5. 是否引入了 Breaking Change？是否有迁移说明？

## 语言常见问题映射

| 维度 | Python 常见陷阱 | Go 常见陷阱 | TypeScript 常见陷阱 |
|------|----------------|-------------|---------------------|
| 安全 | `eval()`/`pickle` 反序列化、f-string SQL 拼接 | `exec.Command` 拼接、未校验的 `io.Copy` | `innerHTML` XSS、`any` 绕过类型检查 |
| 性能 | GIL 下 CPU 密集多线程无收益、`-1` 大列表拷贝 | goroutine 泄漏、未用 `sync.Pool` 反复分配 | 大量闭包致内存泄漏、未 `useMemo` 重复计算 |
| 错误处理 | 裸 `except:` 吞掉全部异常、`finally` 中 `return` | 忽略 `error` 返回值 `_ = do()` | `Promise` 未 catch、回调地狱 |
| 并发 | `threading` 共享状态无锁、`asyncio` 中调同步 IO | `map` 并发写 panic、channel 死锁 | `Promise.all` 一个失败全失败、竞态条件 |
| 依赖管理 | `pip` 无锁定文件、requirements.txt 版本范围过大 | `go.sum` 不一致、replace 指向本地 | `package.json` 版本浮动、`node_modules` 膨胀 |

## PR 评审结构化模板

复制以下内容到 PR 评论区，按实际填写：

```markdown
## Code Review Summary

**结论**：[Approved / Changes Requested / Commented]
**影响范围**：[核心链路 / 边缘功能 / 基础设施]
**风险等级**：[P0 阻塞 / P1 需关注 / P2 建议 / P3 可选]

### 亮点（What's Good）
- ...

### 阻塞项（P0 — 必须修复）
- [ ] 位置：`path/file.ext:line` — 问题描述 — 建议方案

### 关注项（P1 — 当前 sprint 处理）
- [ ] 位置：`path/file.ext:line` — 问题描述

### 建议项（P2 — 可协商）
- ...

### 可选优化（P3 — Nit）
- ...

### 测试验证
- [ ] 单元测试已添加
- [ ] 集成测试已通过
- [ ] 本地手动验证完成

### Follow-up
- Issue 链接（如有）
```

## 建设性 Feedback 模板 — BIC 模型

**Behavior（行为）** → **Impact（影响）** → **建议（Change）**

示例：

> **B**：`get_user_data()` 在循环内逐条查询数据库（`src/services/user.ts:42`）
> **I**：当用户量增长到 10k 时，单次请求将产生 10k 次 DB 查询，响应时间可能从 50ms 退化到 5s+
> **C**：建议改为 `batch_get_users(ids: string[])` 单次批量查询，参考 `src/services/order.ts:78` 的实现模式

使用原则：
- 对事不对人，描述代码而非评价作者
- 给出具体行号/路径，降低定位成本
- 附带改进建议或参考实现，不让对方猜
- 肯定好的一面再提改进，比例保持 1:1 以上

## Review 度量指标

| 指标 | 计算方式 | 健康基准 |
|------|----------|----------|
| 缺陷密度 | P0+P1 问题数 / PR 变更行数 × 1000 | < 2 个/千行 |
| PR Review 响应时间 | PR 创建 → 首条评论的时间中位数 | < 2 工作日 |
| Review 覆盖率 | 经过至少 1 人 review 的 PR 占比 | > 90% |
| 重开率 | 被退回后重新提交的 PR 占比 | < 20% |
| 平均评论数 | 每 PR 有效评论（非 LGTM）数 | 3-8 条 |

## 使用指南

何时引用本 Skill：

- 收到 PR Review 请求时，按维度逐项检查，按 P0-P3 分级标记
- 编写/完善团队 Code Review 规范时，作为基线模板
- Onboard 新成员时，作为 Code Review 培训材料
- 回顾团队评审质量时，用度量指标做量化分析
